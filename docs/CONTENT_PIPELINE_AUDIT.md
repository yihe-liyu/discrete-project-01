# 内容创作流程审查

> 审查日期：2026-10-17（重建于 2026-10-21）
> 范围：关卡编排 / Boss 与阶段 / 弹幕与弹型 / 敌人 / 背景与演出
> 目的：不是再写一份「怎么做」教程，而是回答「五条内容线各自有多自由、加一份内容要碰几处、现在卡在哪」。
> 教程仍以 [CONTENT_GUIDE](../CONTENT_GUIDE.md) 为准；本文只留判断与下一步。

## 0. 结论

当前流程是 **代码优先 + `.tres` 数据 + 工作台实时预览**。自由度不是主要问题：

- 弹幕、敌人、Boss 行为都能直接写 GDScript，不受「波次表 / 模板注册器」限制；
- `.tres` 只承载共享数据（阶段、Boss、关卡、弹型外观），没有变成第二套逻辑；
- 三个组合台能跑真实运行时，支持热更新、固定种子、逐帧和书签。

真正的瓶颈在 **反馈回路** 和 **契约边界**：

1. **关卡 / Boss 仍然靠手写注册表**：漏登记不会编译失败，只会「菜单里看不见」。
2. **整关预览没有热更新**：改时间线要重启，反馈明显慢于三个组合台。
3. **`params` 仍是共享字典**：未知键现在会报，但 move / shoot 同名键仍会互相覆盖。
4. **验证主要靠「跑起来看」**：没有内容级 golden / 截图 / 回放回归。
5. **文档与代码会漂移**：本次审查就发现 `CONTENT_GUIDE` 仍在列已删除的 `BossData.enter_script` / `exit_script` / `score_value`（已修）。

一句话：**不是「内容写不出来」，而是「写错时不够早响、改完到看见的路径不够短」。**

## 2. 五条内容线

### 2.1 关卡编排

**现在怎么做**

- `StageData.tres` 提供 `stage_id` / `stage_no` / `display_name` / `bgm_key` / `create_script` / `background_scene`。
- 关卡脚本 `data/stages/<面>/stage_script/*.gd` 用 `Timeline` 排 BGM、敌人、Boss、阶段、对话事件。
- 可玩面要进 `data/registry/stage_registry.tres`；`StageCatalog.playable()` 只认有 `create_script` 的项。
- 新面通常还要一张背景场景、一个 BGM key，以及 Boss / 阶段内容。

**自由度**

高。时间线是代码，条件、循环、随机、事件都能直接写；没有波次表或可视化时间线强制结构。

**新增触点**

最少 4～7 处：

1. `stage_data/*.tres`
2. `stage_script/*.gd`
3. `data/registry/stage_registry.tres`
4. `background_scene`（新面通常要）
5. `bgm_key`（`AssetRegistry.BGM_PATHS`）
6. Boss / 阶段（若这一面有战斗）
7. 对话脚本（若需要剧情）

**摩擦**

- **注册表是隐式契约**：不登记 `stage_registry.tres`，`StageCatalog.all()` 不会列它；只有按 id `find()` 才会走目录扫描兜底。结果是「代码能跑，菜单里没有」。
- **没有新面脚手架**：目录约定、`StageData` 字段、注册表项、BGM key 全靠人记。
- **整关预览没有热更新**：改时间线 / 关卡脚本要切页或重启；三个组合台反而更快。
- Timeline 的 `wait()` / `start_phase()` 顺序有坑（`wait` 后必须直接链 `start_phase`），这类错误主要靠读文档和试跑发现。

**更好的思路（跨项目）**

- 把「可玩内容清单」做成 **生成物**，而不是手写注册表：扫描 `StageData`，校验 id 唯一、`create_script` 存在、背景 / BGM 可解析，生成或校验 manifest。
- 新面用 **模板 / 生成器**：一条命令建目录、`.tres`、脚本骨架、注册表占位和测试夹具。
- 整关预览的目标不是「也热更新脚本」，而是 **快照 + 重建视图**：保存模拟状态，重载脚本后恢复时间/位置/种子；这比逐脚本热替换更通用。
- **已落地（2026-10-21）**：`StageData.variants` 提供 base + 每难度覆盖（脚本 / 背景 / BGM），先解决「整面难度差异」而不复制整份 StageData。

### 2.2 Boss 与阶段

**现在怎么做**

- `BossData.tres` 带 `boss_name` / `section_label` / `visual` / 各难度 `phases_*` / `spell_background` / `portrait` / `practice_bgm_key` / 全破演出字段。
- `PhaseData.tres` 带 `name` / `uid` / `hp` / `time_limit` / `is_timeout_only` / `move_script` / `shoot_script` / `pre_move_script` / 掉落 / `params`。
- Boss 要进 `boss_registry.tres`；阶段脚本由 `.tres` 显式引用，不自动发现。
- 阶段身份 `(stage_id, phase_index, character, difficulty)` 由 `BossCatalog` 的规范顺序决定，不由 Boss 怎么拆分决定。

**自由度**

高。Boss 可以拆道中 / 关底，阶段可以复用脚本，也可以用 `diff_pick()` 做难度差分。

**新增触点**

一个 Boss 通常 6～8 处：

1. `BossData.tres`
2. `boss_registry.tres`
3. `visual` 场景（可复用）
4. 每个阶段的 `PhaseData.tres`
5. `move_script` / `shoot_script`（可复用）
6. 关卡脚本里的 `_dir.boss(...)` / `start_phase(...)`
7. 可选：`practice_bgm_key`、`spell_background`、`portrait`、全破特效
8. 可选：`pre_move_script`、对话事件

**摩擦**

- **阶段身份与组织方式解耦是优点，也是认知成本**：`boss_slot_count` / 规范顺序 / `phase_index` 需要理解，不能靠目录猜。
- **`params` 共享字典**：`PhaseData.params` 同时注入 `pre_move` / `move` / `shoot`；同名键会同时改两边，未知键现在会报，但同名冲突仍不报。
- **Boss / 阶段注册仍是手写**：Boss 漏登记只在符卡册 / 练习里消失。
- **符卡 UID 靠约定**：全局唯一、分段建议都写在文档里，没有机械校验。

**更好的思路（跨项目）**

- 用 **内容图** 表达 Boss → 阶段 → 脚本 → 弹型 → 资源：注册表只是图的序列化缓存，校验器负责环、悬空引用、重复 UID。
- 把 `params` 从「共享字典」升级为 **命名空间 / 显式 schema**：`move.*`、`shoot.*`、`pre_move.*`，每个脚本声明自己接受的键；冲突在加载期报。
- 阶段编辑器 / 检查器先做 **只读验证 + 预览**，不要一上来做写入式编辑器；写入式编辑器会制造第二套真相。

### 2.3 弹幕与弹型

**现在怎么做**

- 弹型外观 / 碰撞 / 朝向在 `data/bullets/*.tres`（`BulletDef`）；运行时类型是 `BulletType`。
- 发射与飞行用 `BulletData` 构造链 + `BulletLifecycle` 描述符；工作台「拼装页」把描述符拼成代码。
- 弹型缓存挂在 `BulletData` 实例上，同实例 → 同 `BulletType`。

**自由度**

很高。`BulletLifecycle` 是原语组合，不是固定弹型表；内容可以写一次性行为脚本，也可以拼描述符。

**新增触点**

通常 2～4 处：

1. 弹丸行为 `.gd`（若需要逐弹逻辑）
2. `data/bullets/*.tres`（若需要新外观 / 判定）
3. 发射脚本 / 阶段脚本里的 `BulletData` 构造
4. 必要时 `BulletLifecycle` 描述符

**摩擦**

- **最大知识税是求值时机**：哪些参数是建造期常量、哪些每波 / 每弹 / 相位结束求值，只活在文档和源码里；`emit` 在相位结束逐弹求值、`random_dir` 每次求值抽一次 RNG，都是踩过才知道。
- **拼装页只拼 trajectory**：不拼 `_tick` / 波次调度；复杂行为仍要手写脚本。
- **静默覆盖**：preset / builder 如果覆写显式开关（例如 `.enemy()` 改 `is_spawn_fog`），内容作者很难发现。
- **缺少内容级回归**：改一个 lifecycle 原语，影响哪些符卡只能靠跑测试 / 试玩。

**更好的思路（跨项目）**

- 把求值时机做成 **显式作用域**（build / wave / shot / phase-end），而不是靠函数名和注释；DSL 的每个参数都带 scope。
- 给弹幕 DSL 做 **静态检查 + 影响面查询**：某个原语被哪些内容引用、改它会影响哪些 phase。
- 拼装页从「代码生成器」升级为「可回读的中间表示」：生成的代码能被解析回描述符，避免代码成为第二真相。
- 用 **确定性 replay / golden** 做内容回归；同种子同输入下比较事件序列，而不是只比较截图。

### 2.4 敌人

**现在怎么做**

- `EnemyData` 构造链写死外观 / 血量 / 判定 / 掉落；行为脚本由 `EnemyData.with_script()` 引用。
- 生成走 `ctx.enemies.spawn(data)`；回收分静默 / 击破 / Boss 退场三条路径。
- 没有敌人注册表：关卡脚本直接 `preload()` 行为脚本。

**自由度**

高。敌人行为是普通协程，生成参数是代码构造链。

**新增触点**

通常 2 处：

1. 敌人行为 `.gd`
2. 关卡脚本里的 `EnemyData.new().with_script(...)` 生成点

不需要注册表，这是它比 Boss / 关卡轻的地方。

**摩擦**

- **生成点散在关卡脚本里**：没有敌人目录页 / 清单；同一个行为脚本的复用关系只能 grep。
- **参数靠 `param()` 字符串键**：`EnemyData.params` 已严格校验，但键名与行为脚本属性的对应仍靠人记。
- **敌人台能预览，但和真实关卡的时间线上下文不同**：手感 / 密度仍需整关验证。

**更好的思路（跨项目）**

- 敌人「原型」用 **archetype + behavior** 两层：原型是数据（外观/血量/掉落），行为是脚本；生成点只引用原型 key。
- 给行为脚本声明 **参数 schema**，生成器 / 检查器共享；避免 `param("typo")` 只靠运行时校验。
- 敌人台加入「从真实关卡时间线抽一段」的能力，而不只是孤立生成。

### 2.5 背景与演出

**现在怎么做**

- 背景是独立 `.tscn`，根挂 `StageBackground`；相机 / 环境 / 雾 / 装饰物由宿主按类型解析。
- `StageData.background_scene` 指定背景；练习模式复用同一张。
- 背景协程是根的直接子节点 `CoroutineScript`，由 `StageRuntime` 自动启动。
- 对话由 `DialogueSteps` + `ctx.dialogue` / `StageDirector` 事件路由驱动。

**自由度**

很高。树形 / 层数 / 节点名 / 材质归作者；引擎只认「背景宿主」和「演出脚本」两个接口。

**新增触点**

通常 3～6 处：

1. 背景 `.tscn`
2. `BackgroundEnvPreset.tres`（可选）
3. `DecorLayer.tres`（可选）
4. `StageData.background_scene`
5. 背景演出 `.gd`（可选）
6. 对话脚本 + 关卡事件（若需要剧情）

**摩擦**

- **画面线已冻结**：视觉打磨不再投入，但「背景创作接口」仍可优化；两者要分开。
- **三个组合台没有真实 3D 背景**：只有整关预览有背景视口；调弹幕 / 敌人时看不到真实背景。
- **结构自由但缺少样本模板**：背景基础场景只是可选起点，没有强制结构；新作者容易从空白开始。
- **文档 / 场景漂移**：背景字段、演出组件、相机动词都改过名，旧文档容易残留。

**更好的思路（跨项目）**

- 保持「接口固定、结构自由」，但提供 **可选模板 + 检查器**：模板给起点，检查器只报「宿主缺失 / 演出脚本没挂 / 环境预设没声明」。
- 把背景预览接进三个组合台：背景选择是工作台级状态，不是每个 bench 各自实现。
- 对话 / 演出用 **事件表** 而不是散落回调；事件名和 handler 的绑定可被静态检查。
- 视觉验收用 **固定种子 + 同帧截图 + 亮度/跳变指标**，而不是靠肉眼；这条与 BG 画面线冻结不冲突。

## 3. 横向问题

### 3.1 注册表是第二真相

`stage_registry.tres` / `boss_registry.tres` 是手写清单，但目录扫描又能兜底。两套来源导致：

- 漏登记 = 菜单里看不见；
- 扫描兜底 = 「为什么 `find()` 能找到、`all()` 找不到」；
- 测试夹具可以覆盖 catalog，但真实内容仍靠注册表。

**方向**：注册表由扫描生成 / 校验，或明确「注册表是唯一来源，扫描只用于报错」，不要两套都活。

### 3.2 反馈回路不对称

| 内容线 | 反馈 |
|---|---|
| 弹幕 / 敌人 / 阶段 | 组合台热更新，约 1～2 秒 |
| 整关 | 切页保活，改脚本仍要重启 |
| 背景 | 整关预览才能看到真实 3D |

越靠近「整体节奏」的内容，反馈越慢；这正好是最需要反复试的部分。

### 3.3 静默失败面仍然偏大

已经修了很多（`params` 未知键、Boss / 阶段校验、背景缺件告警），但还剩：

- 注册表漏项；
- 阶段 UID 重复 / 越界；
- 共享 `params` 同名键；
- 背景场景缺宿主 / 缺演出脚本；
- 文档字段漂移。

### 3.4 没有内容图

现在能回答「这个脚本被谁引用」主要靠 `ContentCatalog` 的 refs 信息和 grep；不能回答：

- 改这个 lifecycle 原语影响哪些符卡；
- 删这个弹型 / 背景会不会有内容悬空；
- 哪些 Boss / 阶段没有被任何关卡引用。

### 3.5 内容级回归缺失

现有 885 个测试主要保护机制与契约；内容本身只有「结构冒烟 / 不数数量」的测试。结果是：

- 机制改对了，内容手感可能变了；
- 内容改坏了，测试不一定红；
- 视觉回归靠人眼和截图工具。

## 4. 跳出当前项目的更好思路

下面这些不是「本项目特供」，而是内容管线常见的成熟模式；括号里写的是本项目可以先借哪一层。

### 4.1 三层作者模型：逻辑 / 数据 / 摆放

- **逻辑**：代码（Timeline、协程、lifecycle）。
- **数据**：`.tres` / Resource（数值、阶段、Boss、关卡）。
- **摆放**：编辑器（背景树、节点位置、视觉）。

不要试图把三层合成一层。全代码会失去调参效率；全数据会把逻辑塞进 schema；全编辑器会先造一个通用编辑器。**按内容线选择主层，其他层只做覆盖。**

### 4.2 Schema-first + 生成清单

把「内容长什么样」写成 schema / 校验器，而不是靠约定：

- 字段类型、必填、默认值；
- 引用是否存在（脚本 / 场景 / BGM / 纹理）；
- ID 唯一性（stage_id / boss order / phase uid）；
- 可玩性（`create_script` 非空、背景可实例化）。

然后由扫描 **生成** manifest，或至少 **校验** manifest。Unity 的 ScriptableObject、Unreal 的 DataAsset、Godot 的 Resource 都只是存储载体；真正省事的是 schema + manifest + 校验，而不是载体本身。

### 4.3 热重载是架构，不是脚本替换

真正通用的热重载需要：

1. 模拟与视图分离；
2. 可序列化的模拟状态；
3. 重载后恢复状态（时间、位置、RNG、实体表）；
4. 只重建视图 / 资源。

只做「脚本 reload」在简单脚本上有效，遇到状态、协程、缓存就会失效。整关预览可以先用 **快照 + 重进关卡**，不追求逐脚本热替换。

### 4.4 内容也要 golden / replay

- 同种子 + 同输入 → 同事件序列（不是只同截图）；
- 固定相机 / 固定帧号 → 同截图；
- 内容夹具只验证结构，不把真实内容数量写死；
- 给内容作者一个「录一段、回放、对比」的按钮，比让他们手算更可靠。

### 4.5 脚手架与模板

新内容最常见的错误不是「写错逻辑」，而是「漏了一个注册 / 少了一个字段」。一条命令生成：

- 目录 + `.tres` 骨架；
- 脚本骨架 + `@role` 注解；
- 注册表占位；
- 一个最小测试 / 预览入口；
- 检查清单。

模板不是限制自由度，而是把「必填项」从记忆变成生成物。

### 4.6 内容图与影响面

把内容当图：关卡 → Boss → 阶段 → 脚本 → 弹型 / 背景。图能回答：

- 改一个原语影响哪些内容；
- 删一个资源哪些引用会断；
- 哪些内容没人引用。

这不一定要上数据库；一个扫描生成的 JSON / Resource 就够，先做只读。

### 4.7 给管线本身做度量

至少记录：

- 新增一条内容要改几处（触点数量）；
- 改完到看见的秒数（反馈延迟）；
- 内容相关失败中「静默失败」占比；
- 内容回归的红/绿时间。

没有度量，优化会变成凭感觉。

### 4.8 不要过早造通用编辑器

写入式编辑器成本高，而且容易变成第二套真相。先做：

1. 只读检查器；
2. 预览 / 热重载；
3. 生成器 / 脚手架；
4. 最后才是写入式编辑器。

当「同一类内容每月都要手工改 10 次以上」时，再考虑编辑器。

---

## 5. 建议顺序

### P0：先把「漏了就消失」变成「启动就报」

1. **内容 manifest / 校验器**：扫描 StageData / BossData / PhaseData，校验 ID、引用、可玩性；`verify` 接入。
2. **新内容脚手架**：新面 / 新 Boss / 新阶段模板，生成注册表占位与最小检查。
3. **`params` 命名空间**：至少禁止 move / shoot 同名键，报错信息指出冲突键。
4. **文档漂移检查**：像本次这样，用脚本检查关键字段清单是否还在代码里。

验收：漏注册 / 悬空引用 / 重复 UID 在 `verify` 阶段红，而不是等人打开菜单发现。

### P1：缩短反馈回路

5. **整关预览快照重进**：保存时间 / 种子 / 关卡，重载后恢复；先不做逐脚本热替换。
6. **三个组合台接入真实背景**：背景选择做成工作台级状态。
7. **内容图只读视图**：引用 / 被引用 / 孤儿，先给作者看，不自动改。

验收：改时间线到看见 ≤ 5 秒；调弹幕时能看到真实背景。

### P2：内容级回归与编辑器

8. **确定性内容回放 / golden**：同种子事件序列 + 固定帧截图。
9. **只读阶段 / Boss 检查器**：展示规范顺序、UID、引用、params 冲突。
10. **写入式编辑器**：只在 P0/P1 稳定后做，且必须从同一 manifest / schema 读写。

验收：机制改动导致内容行为变化时，CI 能指出受影响的 phase；编辑器不会产生第二套数据。

---

## 6. 不建议现在做

- **不要把所有逻辑数据化**：Timeline / 协程 / lifecycle 的表达力来自代码；强行 schema 化会先失去自由度。
- **不要先造通用编辑器**：没有 manifest / 校验 / 预览之前，编辑器只会把手工错误藏得更深。
- **不要保留两套注册真相**：手写注册表 + 目录扫描兜底只能留一个作为主来源。
- **不要强制背景结构**：背景线已经证明「接口固定、结构自由」是对的；模板只能可选。
- **不要把 `params` 当主分化手段**：难度轴优先 `diff_pick()`，内容轴优先另写脚本。
